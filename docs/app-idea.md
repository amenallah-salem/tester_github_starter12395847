# Welora (Gym Planner) — App Idea

> Living doc: the source of truth for *what we're building and why*. Read
> this alongside `CLAUDE.md` (the *how the code is structured* doc). Keep
> both updated when the product direction changes — an outdated app-idea
> doc is worse than none, because Claude and teammates will plan against it.

## One-line pitch
An AI personal trainer app: a Flutter mobile/web app with a Django backend,
where a user gets a personalized weekly training plan, runs their workouts
against it, logs progress, and gets coaching/recovery support around the
workout itself — not just a static plan tracker.

## Who it's for
Someone who wants structured, ongoing training guidance without hiring a
human coach — beginner-to-intermediate lifters who want a plan that adapts,
reminds them why an exercise matters, and helps them recover, rather than a
bare "log your sets" spreadsheet-style app.

## Current status (be honest about this in every planning conversation)
This is a **working scaffold with real infrastructure but mixed feature
depth**. Some things are production-shaped; some are UI-only mockups
waiting for the real logic behind them. Concretely, as of this doc:

| Feature | Status |
|---|---|
| Auth (JWT), onboarding, profile | Real, backend + frontend wired |
| Weekly plan structure (`Plan`→`PlanDay`→`Exercise`) | Real, backend + frontend wired |
| Exercise library (search/filter by body part, muscle, movement) | Real |
| Workout sessions + progress metrics (sets/reps/weight logging) | Real |
| Body-weight tracking, favorites | Real |
| Billing / subscriptions | **Stub** — model + endpoints exist, no real payment provider wired up |
| AI Coach ("Kaori") — plan generation | **Not implemented** — see "AI Coach contract" below; UI (`coach_page.dart`) exists, no logic behind it |
| Form Vault / 3D biomechanical replay | **Mockup only** — UI + fake data (`biomechanics_mock.dart`); no real pose/CV pipeline |
| Gym Bro (social workout-partner matching) | **Partially real** — profile fields (`bio`, `training_goals`, `experience_level`, `availability`, `location`) exist on the backend `Profile` model and have a settings UI; no matching/discovery logic yet |
| Recovery / breathwork | **Mockup only** — UI with mock metrics, not tied to real session data |

Don't assume any "stub"/"mockup" item works end-to-end just because there's
a nice screen for it. Check `CLAUDE.md`'s feature list before building on
top of one.

## The core idea worth protecting: the AI Coach contract
The plan a user follows is meant to be **generated by an external AI coach
service** (via OpenRouter), not hand-built by us per user. That generated
plan has to conform to a strict JSON Schema —
`frontend/assets/plan_contract.schema.json` — so the app can render it
reliably regardless of which model produced it. The Dart side
(`plan_contract.dart`, `plan_validator.dart`) parses and validates against
that exact shape. Right now, `sample_plan.dart` fakes a valid AI response so
the rest of the app is testable end-to-end without the real AI service.

**This is the highest-leverage, highest-risk integration point in the
product.** When the real AI coach service exists, it must produce JSON that
validates against that schema — and if the schema needs to change to
support a new plan feature, three things move together: the schema file,
the Dart contract classes, and the validator. (See the
`plan-contract-change` skill.)

## Product pillars (what "done" looks like per area)
1. **Plan** — user gets a structured weekly plan (already modeled), ideally
   AI-generated and adaptive over time, not static.
2. **Run** — user executes a workout day with sets/reps/weight/timers,
   logging as they go (`plan_runner` feature — timer + freestyle mode exist).
3. **Progress** — historical view of sessions, body weight, and per-exercise
   trends (`progress` feature — real, backend-backed).
4. **Coach** — conversational or automated coaching around the plan
   ("Kaori" persona) — currently just a UI shell.
5. **Recovery** — post-workout guidance (breathwork, mindful recovery) —
   currently mock UI, intended to eventually use real session data
   (duration, intensity) to tailor recovery suggestions.
6. **Biomechanics** — form-check / movement quality feedback (Form Vault,
   3D replay) — currently mock UI, architecture is placeholder for a future
   computer-vision or pose-estimation pipeline.
7. **Gym Bro** — social layer: find a training partner with compatible
   goals/experience/schedule — backend fields exist, discovery/matching
   logic doesn't yet.
8. **Monetization** — subscription gating of premium features (stubbed
   `Subscription` model + `billing.py`, no live payment provider).

## Non-goals / explicit constraints
- **Privacy**: precise geolocation is intentionally never collected for Gym
  Bro — city/area-level text only (see `Profile.location` comment in
  `models.py`). Keep this constraint if you build matching/discovery.
- **No parallel profile model** — Gym Bro fields live on the existing
  `Profile`, one source of truth per user. Don't create a second profile
  table for a new feature area without a strong reason.
- Local-first on the frontend: features should default to working offline
  via Drift unless they inherently need the server (auth, AI generation,
  social matching, billing).
